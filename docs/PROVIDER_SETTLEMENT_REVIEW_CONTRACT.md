# Provider settlement review — offline normalized contract

AF-SETTLEMENT. Synthetic-only until the CA and finance operator approve source mapping and private local handling. No provider API, bank connection, database access, approval or settlement-state write. A candidate is not proof that funds reached the bank. See Razorpay's public description of settlement reports: https://razorpay.com/blog/how-to-use-razorpay-dashboard/ . This is an internal normalized contract, not a claimed Razorpay CSV schema.

Node 22 command: node scripts/settlement-review.mjs < synthetic-batch.json

Top-level fields: version=1, currency=INR, application, movements, settlements, credits. Each collection is an array. Every row uses an opaque local id. Application rows contain id, kind (capture/refund), reference (unique provider payment/refund reference within kind), amountPaise (positive integer whole charge or refund, not donation principal). Movements contain id, settlementId (opaque local settlement id), kind, reference, amountPaise. Capture/refund reference must match the application's typed provider reference; fee/tax/adjustment_credit/adjustment_debit reference must be null. Fee/tax/refund/adjustment_debit subtract from the batch; capture/adjustment_credit add. Do not infer any amount from advertised fee rates. Settlements and credits contain id, reference (normalized exact bank UTR), amountPaise. Supply only independently identified positive payouts and incoming credits, never a guessed payout or a debit.

Synthetic example: application capture PAY001 10000 paise, refund REF001 1500; settlement s1 contains these movements plus fee 200 and tax 36; declared settlement UTR001 8264 and bank credit UTR001 8264 yield one candidate. This is an example, not an actual provider charge.

Candidate requires all linked capture/refund references and amounts uniquely matched, linked movements present, their signed sum equal to declared payout, and exactly one bank credit of the same UTR and amount. Explicit adjustments always require review even if the sum ties. Duplicate transaction or bank references, unmatched amounts and missing data are exceptions. Unlinked movement IDs, unmatched application IDs, and credit IDs not consumed by a complete candidate are separately returned. An otherwise consistent batch can remain a candidate despite unrelated exceptions, so review the entire report. The summary is not bank balance or total donation income. An empty batch is not a complete reconciliation.

The independently selected account, reporting window, source report types, units, unique provider IDs, direction and distinction between actual credit and failed/pending settlement must be reviewed before normalization. Do not assume settlement and bank posting dates are identical. Do not upload actual reports to a chat, repository or CI. Use opaque local ids, keep reference mapping and input/output in restricted local storage. No donor identity, free text, raw payload, account number or credentials. Input bounded to 32 MiB and 100,000 rows per collection; safe integer paise and unknown fields refused. Output never includes input reference fields. Never infer ownership or source completeness from this calculation. No split/partial settlement or merged bank credit support. Only externally approved review can resolve exceptions.

Tests: node --test scripts/test-settlement-review.mjs . O(n) expected time and space in total input rows. No added dependencies. Actual provider/bank mapping and accounting acceptance remain outstanding.

## Shared bank-credit review across channels

Use `node scripts/cross-channel-credit-review.mjs < synthetic-batch.json` for a single combined review, rather than summing independent direct and provider candidate totals. It accepts the same version 1 INR `application`, `movements` and `settlements` collections, plus `claims` and one `credits` collection in the shape defined in [DIRECT_CREDIT_REVIEW_CONTRACT.md](DIRECT_CREDIT_REVIEW_CONTRACT.md) (each credit includes a normalized Indian calendar `day`). Both channels must belong to the same independently reviewed account scope and reporting period. This shared feed is not independently verified or presumed complete. A case-sensitive reference present in both direct claims and declared payouts is quarantined on both sides even if one channel fails its amount/date/evidence check or the bank credit is missing. Duplicate bank references remain exceptions; each bank credit can contribute to at most one channel. Candidate and exception totals conserve the supplied positive credit pool in integer paise. Provider unmatched application/movement diagnostics remain separate; a matched application movement does not certify the payout. Output retains opaque ids, counts and amounts, not references. Never combine separate account or period reports without reviewed source mapping. No payment, approval, DB, bank/provider integration or real records. Same input limits and private handling as the component contracts; synthetic-only until approved source mapping and finance acceptance. Regression: `node --test scripts/test-cross-channel-credit-review.mjs`.
