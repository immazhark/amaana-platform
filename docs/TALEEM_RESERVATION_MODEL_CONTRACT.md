# Taleem reservation — unpublished synthetic model

AF-SPONSOR groundwork. Not production inventory or payment authorization. The existing programme catalogue is not a capacity catalogue and the published learner count is not available inventory. The model requires explicit synthetic units per programme per calendar month; 1/3/6/12 month terms and 1–50 units follow the current programme quote shape. A proposed hold can only be a candidate if every month fits. Expiry uses a supplied clock in integer epoch milliseconds; at expiry, a held record consumes no inventory, but a committed record still consumes its full term. Released rows remain identifiers, not availability promises. A replay must preserve all original request fields and cannot extend a hold; an expired request is refused. Missing or inconsistent data fails closed. The algorithm is O(C + 12R) expected time, O(C + R) space, with bounded input collections. It is pure, uses no clock, datastore, identity or provider, and is advisory only: concurrent callers can both see the same available capacity. Do not expose a route, persist a hold, derive actual places, link a student, reserve payment inventory, consume provider callbacks, or activate expiry jobs from this model. A future separately approved design must establish capacity ownership, atomic transaction/concurrency protection, duration and expiry policy, renewal/refund/cancellation and late-payment handling, auditable idempotency and privacy boundaries before implementation. No real reservation or sponsorship obligation has been created.

Test: `node --test scripts/test-taleem-reservation-model.mjs` (synthetic only).

## Synthetic lifecycle extension

The pure transition evaluator consumes one held/committed/released row, matching immutable request evidence, an explicit action (confirm/release/expire) and supplied integer time. It does not establish that the row, clock or evidence is authentic or current. Confirming a live held row proposes committed; at or after expiry the result is late_confirmation without reacquiring capacity. A released row cannot be confirmed. Repeat confirmation of an already committed row with matching terms is unchanged even after expiry. Expiry and ordinary release never free committed inventory; release of committed inventory requires a separate reviewed refund/cancellation/allocation decision. Uncommitted expiry at the exact boundary or explicit release proposes released, and repeat release/expiry is unchanged. Changed identifiers, programme, start month, term, units or expiry are refused; malformed inputs fail closed. The result is advisory, contains no private data and makes no mutation. The proposal does not perform capacity revalidation, payment verification, authorization or compare-and-set. A future approved transactional caller must atomically verify all of those conditions against current inventory and trusted evidence. Do not expose this model as a production route, reservation, financial or provider callback handler. No new live policy is approved by these synthetic rules.

## Synthetic ordered batch proposal

`evaluateHoldBatch` accepts one snapshot and 1–50 distinct, unexpired synthetic requests. It validates the complete request set and inventory before evaluating requests in supplied order; existing exact held/committed replays add no new units. Each new proposal consumes units in the private working map before the next request is evaluated. Any missing capacity, conflict or insufficient month returns only the failure and zero partial proposals; a successful batch returns newly proposed held rows. Inputs are unchanged. Expected time O(C + 12R + 12B), space O(C + R + B). This is an offline all-or-nothing calculation, not database atomicity, a reservation or a guarantee against concurrent callers. Do not use real sponsor records, expose a public route or activate checkout/expiry. Existing single-hold and transition semantics are unchanged. The existing native test command includes the batch regression module.
